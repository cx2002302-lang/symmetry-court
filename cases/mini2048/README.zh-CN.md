# 案卷 `mini2048` —— 2048 合并机制 · 2×2 确定性变体

引擎 **explicit** 口径（状态置换 + 逐动作声明映射）的第一个真实系统样本——
也是本仓库第一个被确定性复现的引擎缺陷现场。

一键复现全部案卷：
`python -X utf8 cases/mini2048/make_mini2048.py --check`（字节自证 + 穷举对称
自证，退出码 0）。

## 模型

原版开源 2048（[gabrielecirulli/2048](https://github.com/gabrielecirulli/2048)，
MIT）的确定性核心：滑动 + 合并，不收录随机生成块（随机性不在确定性 FSM 语义内）。
每条生成规则都在 `model.json → meta.rules_with_citations` 里引一手出处
（`js/game_manager.js` 行号锚点：`move()` L130-191、方向编号 "0: up, 1: right,
2: down, 3: left" L131、合并条件 L156、合并取值 L157、得分 L167、无效移动
L175-177/L182、随机生成 L182-183 + L68-76、无路可走 L184-187/L238-268），
并以 Wikipedia Gameplay 段原句互证。

- 256 态 = 2^8（4 格 × 2 bit；格编码 0=空, 1=值2, 2=值4, 3=未用）。
  81 个真态 + 175 个不可达填充态（全动作自环、奖励 0）。
- 4 动作 = 方向键，沿用原实现的编号。
- 奖励 = 2048 计分：唯一允许的合并（2+2 → 4）记 +4，其余 0
  （`score += merged.value`，game_manager.js L167）。变体边界：一步含两次
  2+2 合并时记 +4（按原版逐次累加应为 +8）；转移完全一致，无判决依赖此差。
- 变体边界（见 `meta.transcription_notes`）：合并上限取 4（两个 4 不合并——
  原版任意等值对都合并）；随机生成块未收录；死盘全动作自环（这正是原版
  `move()` 对"什么都没动"的移动的计算结果）。

## 棋盘对称群与 explicit 口径

2×2 棋盘的对称群是 D4（8 阶）。真棋盘对称会**连同格子一起改方向键的名字**：
棋盘顺时针转 90° 后，原来的"上"键就是现在的"右"键。每个群元素 π 的改名
ρ(π) 是**被 forced 的**，且 π ↦ ρ(π) 构成群同态。`make_mini2048.py` 在 24 个
动作双射中穷举推导每个 D4 元素的 ρ(π)，并断言唯一性与同态律（每次运行都验）。
已验证的映射表：

| 元素 | 内容映射（格） | forced 动作映射（上,右,下,左） |
|---|---|---|
| 恒等 | [0,1,2,3] | [0,1,2,3] |
| 顺时针旋转90° | [1,3,0,2] | [1,2,3,0] |
| 旋转180° | [3,2,1,0] | [2,3,0,1] |
| 逆时针旋转90° | [2,0,3,1] | [3,0,1,2] |
| 上下翻转 | [2,3,0,1] | [2,1,0,3] |
| 左右翻转 | [1,0,3,2] | [0,3,2,1] |
| 主对角转置 | [0,2,1,3] | [3,2,1,0] |
| 反对角转置 | [3,1,2,0] | [1,0,3,2] |

## 发现（2026-11-03；队长裁决：按 observed 如实记录，引擎修复归下一波上游）

vendored 引擎的 explicit 判据（`vendored/wuxing_gua/core_check.py` L249-267
`_equiv_error_explicit`，接线在 L317-354 `_check_transition`）把**一个**声明的
`action_map` 用于闭包群的**每一个**元素——包括恒等元；而 `close_group`
（L114-135）必然把恒等元补进闭包，全元素检查（阶 ≤ 5000 → `all_elements`）
必然查它。

对恒等元，explicit 判据退化为 `dist(s,a) = dist(s, ρ(a))`（对所有 s, a）。
在本模型上（也在任何动作两两可分辨的系统上——盘上放一个块就能分离任意两个
方向），这强制 ρ = 恒等映射。但旋转 90° 元素需要 ρ = [1,2,3,0] ≠ 恒等。矛盾：
**任何**声明的映射都不可能让非平凡的"动作改名"对称通过。这正是 explicit 口径
零真实系统样本的原因。

Live 证据（与法庭完全一致的调用：`vendored/` 目录下
`python -X utf8 -m wuxing_gua check`，不带 `--strict`；收据在 `receipts/`）：

| 群 | 声明 | 阶 | 引擎判决 | 指纹 | 轨道（压缩） |
|---|---|---|---|---|---|
| `g1_rot90_map` | explicit，rot90cw 的映射 | 4 | 拒答 | 3/4 元素不过，`first_bad` = **恒等元**，tv 1.0；奖励层通过（n_bad 0） | 70（3.657×） |
| `g2_rot90_nomap` | fixed（键钉死） | 4 | 拒答——*正确* | `first_bad` = rot90 元素 | 70（3.657×） |
| `g3_flip_map` | explicit，flip_tb 的映射 | 2 | 拒答 | 1/2 不过，`first_bad` = **恒等元** | 136（1.882×） |
| `g4_d4_full` | explicit，全 D4 | 8 | 拒答 | 7/8 不过，`first_bad` = **恒等元** | 55（4.655×） |
| `g5_row_mirror_fake` | fixed，对照 | 2 | 拒答——*正确* | 只翻上排的"镜像"在任何口径下都不是对称（生成器断言连 ρ 都不存在） | 160（1.600×） |
| `g6_pads` | fixed，填充态对换 | 2 | **放行**（exit 0，worst_tv 0.0） | 阳性对照：模型良构 | 255（1.004×） |
| 对照：g1 改恒等映射 | explicit，[0,1,2,3] | 4 | 拒答 | `first_bad` = rot90 元素——排除"映射选错了"的备择解释 | 70 |

指纹解读：g1 死在自己的恒等元上（g4 死在 7/8），而按某一生成元映射检查时唯一
能过的元素恰是该生成元本身——这是"单全局映射"设计局限的精确指纹，不是转录
错误。同一模型上 `g6_pads` 放行，排除了模型层面的坏损。

**后果。** g1/g3/g4 在逐元素动作映射语义下是真对称（已推导并机器断言）；引擎
explicit 层拒绝它们，是因为其群文件格式表达不了逐元素映射。上游修复后
（逐元素 ρ(π)，且满足同态律 ρ(gh)=ρ(g)∘ρ(h)），这三群的 explicit 口径收据
预期**翻案为放行**；g2/g5 预期维持拒答（fixed 口径），g6 维持放行。
`expected.json` 里的 relabel/fixed 行答的是别的口径，不预期翻案——各行自带
`note` 说明。`expected.json → groups.*.note` 与
`model.json → meta.known_issue` 均指向本文件。

## 文件

- `make_mini2048.py` —— 确定性生成器；`--check` 重跑对称自证并核 8 个文件的
  字节一致。
- `model.json`、`expected.json`、`groups/g1…g6.json` —— 案卷本体。
- `receipts/check.<群名>.json` —— 每群一份 live 引擎收据（不带 `--strict`）；
  `receipts/check.control_g1_identity_map.json` +
  `receipts/_control_g1_identity_map.group.json` —— 恒等映射对照实验
  （临时群文件，留证不属案卷六群）。
- 法庭收据：`verdicts/mini2048.verdict.json`（三方庭审）。
