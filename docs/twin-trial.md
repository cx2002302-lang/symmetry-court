# The Twin Trial — a symmetry claim put in front of three judges

*The complete account of this repository's flagship case: TCP's CLOSING and
FIN-WAIT-2, the pair of states that look like twins on the wiring diagram and
behave like strangers in the specification.*

Every number in this document is backed by a receipt file in this
repository — the case file `cases/tcp/` (model, groups, expected records)
and the trial records `verdicts/tcp.verdict.json` — and the gate
(`python -X utf8 -m symmetry_court selftest`) re-verifies the match on
every run.

---

## 1. One-sentence summary

A structure-only reading of the TCP state machine says two states are
interchangeable; a reading that keeps event names fixed says they are not;
both are right, and the entire value of the exercise is that the two readings
now sit side by side in a verdict file instead of one of them hiding inside a
tool's default.

## 2. The cast: the twins

Transcribed from RFC 9293 §3.3.2, Figure 5 (the TCP connection state
machine), the closing half of the diagram contains this crossed diamond:

```text
                    --rcv ACK of FIN--> FIN-WAIT-2 --rcv FIN-->
FIN-WAIT-1 /                                                \ TIME-WAIT
                    --rcv FIN---------> CLOSING    --rcv ACK of FIN-->
```

`FIN-WAIT-2` and `CLOSING` are structural twins:

- each has exactly one entrance and one exit;
- both exits lead to the same state, `TIME-WAIT`;
- what sends one twin out is exactly what brought the other twin in.

Erase the event labels and the two states are interchangeable — swap them and
the diagram maps onto itself. Keep the labels and they are strangers: the
event that completes `FIN-WAIT-2` is `rcv FIN` — *the peer hung up on us* —
while the event that completes `CLOSING` is `rcv ACK of FIN` — *the peer
confirmed our hang-up request*. Two different moments of two different
closing paths, printed in a public standard that anyone can open and check.

## 3. Why the defendant is a public standard

Every model tried against the judge engine before this case was hand-made by
the same people who built the judge. That is not fraud, but it is
self-testimony: a model you wrote yourself can silently encode the assumptions
you want to test. The fix is an external referee:

- the machine is **printed in a standard** — 11 named states and their
  transitions, checkable by any stranger with the RFC open;
- it contains a famous **looks-symmetric spot** — the crossed diamond above —
  so it is a fair test of whether the machinery confuses structural likeness
  with behavioral sameness.

## 4. The transcript, and what was deliberately not collected

The case file (`cases/tcp/model.json`, generated by `cases/tcp/make_tcp.py`)
holds 16 states — 11 real ones named
by the RFC plus 5 unreachable padding states,
because the engine's bit-string convention pads up to a power of two — and
20 transitions across 12 distinct
events. Two transcription decisions matter for reading the verdicts:

- **Figure 5 is a summary, and the RFC says so.** Note 3 of the figure
  explains that the "RST from any state" transitions are omitted from the
  diagram. Those edges are therefore **not collected**; the omission is
  recorded in the case's `meta.transcription_notes` rather than silently
  repaired by invention.
- **Rewards are all zero.** TCP defines no payoff, so the reward layer of the
  model carries no information; every conclusion in this case comes from the
  transition layer alone. This is stated rather than hidden because a zeroed
  reward layer makes the reward checks vacuous-by-design, not meaningful.

Each edge carries its clause-level citation; the transcription notes record
anything uncertain as not collected instead of guessing.

## 5. The trial day

The claim put on trial ("defendant group" `swap` in `cases/tcp/groups/`):
*swapping CLOSING and FIN-WAIT-2 maps every transition onto a transition.*

Three independent judges heard it:

| judge | question it answers | verdict |
|---|---|---|
| engine, relabel standard | may event names be renamed along with the states? | pass (exit 0, worst_tv 0.0) |
| engine, fixed standard | must event names stay put? | reject (exit 1, worst_tv 1.0) |
| networkx jury, labeled | same graph question, computed independently, labels held fixed | not a symmetry — identity only |

For contrast, the docket also heard two defendants expected to lose — a
pointless swap (`other`) and an absurd one (`absurd`) — and both were
rejected under both standards (4/4 rows reject in `cases/tcp/expected.json`).
A court that
only hears losing defendants is a rubber stamp in reverse; both kinds of
check belong in the record.

The jury also answered the naive version of the question: counting
**structure-only** automorphisms of the TCP graph finds
2 (on the 11-state protocol subgraph; 240 if the 5 interchangeable padding
states are counted), among them the twin swap; counting them
**with event labels** finds only the identity, 1 (120 counting padding).
That gap — between what the shape allows and what the labeled reality allows
— is the entire story of this case, measured.

Full per-group rows (exit code, verdict, `worst_tv`, judge used) are in
`cases/tcp/expected.json`; the run records are in `verdicts/tcp.verdict.json`.

## 6. Where the disagreement lives

The engine's relabel-side judge searches, for each renamed state and action,
for *some* action at the renamed state that reproduces the renamed successor —
it does not require the action to be the same one. That is a legitimate
modeling choice: for systems whose actions are bound to state coordinates
(switch boards, milestone bits), it is the *correct* choice, because renaming
the coordinates must rename the instructions with them.

The fixed-side judge demands the action itself survive: `π(T(s,a)) =
T(π(s),a)`. For event-driven machines — TCP is the textbook case — that is the
correct choice, because events belong to the world outside the machine, which
no internal renaming can touch.

The twin swap passes the relabel reading only because `rcv FIN` and
`rcv ACK of FIN` are allowed to exchange names — precisely the exchange the
specification forbids. The disagreement between the columns is not noise; it
is the two standards doing their jobs on a case where their assumptions
diverge.

## 7. The detour that proved the point

The obvious "fix" — make the strict reading the only reading — was tried, and
it broke the other half of the world: coordinate-bound systems that any
engineer calls symmetric started getting rejected, because the strict reading
forbids the instruction-manual rewrite those systems require. The conclusion
was not "tune the strictness" but **the assumption about action names must
become an explicit input**. That is why every defendant group in this
repository carries a `semantics` declaration, and why the court always runs
*both* standards instead of electing one. (The upstream engine additionally
honors a `--strict` flag and a group-file declaration; the court's columns
make the choice visible in the output either way.)

## 8. The closed loop

What makes this a trial rather than an anecdote:

1. **The claim is transcribed** from a public standard, edge-by-edge, with
   citations, omissions recorded (§4).
2. **The standards are explicit** — every group declares its semantics; the
   court runs both columns (§6–7).
3. **The jury is independent** — the networkx column is computed by separate
   code from the engine, so a bug in either shows up as a column
   disagreement instead of a shared blind spot.
4. **Everything is replayable** — `python -X utf8 -m symmetry_court selftest`
   re-runs every check and compares field-by-field against
   `cases/*/expected.json`; exit 0 means the verdict files, the expected
   files, and this narrative all still agree.
5. **The disagreement is published, not resolved by fiat** — the twin swap's
   relabel column and fixed column point different ways, on purpose. The
   verdict file records an explicit agree/disagree line and why.

## 9. Reading the receipts

- `cases/tcp/model.json` — the transcribed machine (states, transitions,
  event names, padding, zero rewards, provenance metadata).
- `cases/tcp/groups/*.json` — the defendants, each with a plain-language
  `meta.claim` and a `semantics` declaration.
- `cases/tcp/expected.json` — the expected verdict table: per group, per
  standard: `exit` / `verdict` / `worst_tv` / `judge`, plus the jury columns
  (`structure_symmetry`, `labeled_symmetry`).
- `verdicts/tcp.verdict.json` — the actual trial record produced by
  `python -X utf8 -m symmetry_court arbitrate`.

Engine exit codes, if you read raw records: `0` pass, `1` reject, `2`
sample-shortfall (sampling mode only; not used by this court), `3` input or
internal error.

## 10. What you must not do with this verdict

Do not read the relabel column's pass as permission to merge the twins. Under
the relabel standard the pass says only: *if you are also willing to rename
events, the shape survives*. For TCP you are not, so the operative columns
are the fixed one and the jury's: the twins are not interchangeable, and a
compression that merges them stops being TCP. If your own system's actions
are coordinate-bound rather than event-like, the reading flips — that call is
yours to make explicitly, and `which-identical.md` is the checklist for it.
