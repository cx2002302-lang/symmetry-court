9 案 32 群（compare v2：闸门臂按各群声明口径对账；2026-11-04 起兼容逐元素 action_maps，见下方"口径尊重"节）。朴素臂（只看结构）共放行 12 次合并——其中 7 次恰好安全（填充态对换，压缩 1.004–1.143×），2 次是陷阱：TCP 孪生对（FIN-WAIT-2 ↔ CLOSING，6 格）与 2048 案键钉死的 90° 旋转（740 格）。2048 案的另外 3 个声明口径主张（g1/g3/g4）闸门放行——2026-11-03 它们曾因引擎 explicit 层的单映射局限被误拒，上游 2026-11-04 以逐元素 action_maps 修复后翻案兑现（下节详述）。闸门臂放行 10 次全部零破坏，总耗时约 5.6 秒（32 群 9 案，单机实测求和，精确值见 json）。
一句话：闸门不是每次都救命——它救的正是"结构一样、事件不一样"这一类你用眼睛和结构工具都看不出的坑；其余时候它花几秒钟给你一张"压缩无害"的收据。（它也曾误拒：mini2048 案 2026-11-03 当场抓到引擎 explicit 层的单映射局限，误拒全程公开记录；上游 2026-11-04 修复后 g1/g3/g4 翻案兑现，见下节——错判史同样保留，不删。）

诚实声明（四条）：① 朴素臂是决策方式的代理（"结构像就合并"），不是某个具体第三方工具——但这正是 networkx 不带标签口径的同类做法，TCP 孪生案里它确实判"可换"；② "破坏格"按该群声明口径逐格对账计（合并后行为会改变的 (状态×事件) 数）：带 * 的行是 explicit 群按其声明口径改名事件后对账——2026-11-04 起声明为逐元素映射（每元素配各自的 ρ，g1/g3/g4 全为 0，与引擎放行判据同口径），其余行按事件名钉死口径；fixed 口径对照数在 comparison.mini2048.json 的 broken_real_cells_fixed（g1=740、g3=130、g4=1480）；协议类案卷奖励全零，判定全在转移层；③ 闸门放行群破坏格恒为 0 是判据的数学性质（pass 要求逐格 TV≤1e-9），不是本次运行的巧合。闸门耗时为单机量级记录，精确值在 comparison.*.json；④ 历史（2026-11-03 收据，保留）：当时群文件只能带一个单全局 action_map，g1/g4 的对账数（500/1240）是"把 rot90 的映射强加给闭包群每个元素"的结果，闸门据此误拒三个真对称——上游 2026-11-04 逐元素 action_maps 修复后，g1/g3/g4 按各自映射逐格对账为 0 并翻案放行（收据 cases/mini2048/receipts/）；g2 键钉死 740 格、g5 假群 190 格照旧拒答，g6 照旧放行。mini2048 本次放行 g1/g3/g4/g6，压缩读数均为实跑轨道读数。

怎么复跑

compare 已是法庭正式子命令（纯标准库；v2 起按群声明分派口径：explicit 群原样跑、fixed/无声明群 --strict）：
# 法庭自有九案（含 mini2048 与收编五案）
python -X utf8 -m symmetry_court compare

# 任意同格式案卷集（例：实战盲测五案的原始目录）
python -X utf8 -m symmetry_court compare --root <cases目录> --out <输出目录>
退出码 0 = 对比完成且「放行群零破坏、拒答群全部有据」一致性成立。逐案收据：verdicts/comparison.<case>.json；汇总：verdicts/comparison.summary.json。

2048 正控案：从击穿单映射局限到翻案兑现（2026-11-03 发现 → 2026-11-04 修复）

翻案兑现（2026-11-04，上游 wuxing-gua 逐元素 action_maps 修复落地本仓 vendored 引擎）：群文件 explicit 声明现支持 action_maps——与 elements 一一对应的逐元素动作映射，装载时校验同态律 ρ(g∘h)=ρ(g)∘ρ(h)（≤500 元素全检有序对，本仓六群全为 homomorphism_checked=full）；旧单 action_map 行为不变、标 deprecated。g1/g3/g4 按声明口径翻案放行（实跑收据 cases/mini2048/receipts/，引擎不带 --strict）：g1 order 4、70 轨道（压缩 3.657×）、g3 order 2、136 轨道（1.882×）、g4 全 D4 order 8、55 轨道（4.655×），worst_tv 全 0；g2（键钉死）/g5（假群）维持拒答、g6 维持放行，恒等元对照实验（单恒等映射 → 仍拒于 rot90 元素）照旧成立——legacy 行为不变的直接证据。compare 台账随之更新：闸门放行 7 → 10（放行群破坏格恒 0），朴素臂有害放行 5 → 2（"被救下的合并"从 5 降回真陷阱 2：g1/g3/g4 此前计入"被救"实为引擎误拒，修复后归位为正常放行），朴素臂真破坏格 2486 → 746。一致性 PASS。
为什么 2048 的 D4 是真对称：棋盘转 90° 后按"改了名的方向键"玩，游戏一毫不差——状态置换 π 与方向键改名 ρ(π) 一一配对，π ↦ ρ(π) 满足群同态律。8 个 (π, ρ(π)) 配对由案卷生成器在 24 个动作双射中穷举推导并机器断言（唯一性 + 同态律，每次 make --check 重验）；群文件现按逐元素映射完整声明这 8 张表，引擎装载时独立重验同态律。这是 explicit 口径的第一个真实系统样本，也是"放行方向"的第一个非平凡真对称案卷。
翻案史（2026-11-03 记录，原文保留——诚实传统，不删）：当时 vendored 判官的 explicit 层把一个声明的 action_map 用于闭包群每一个元素——含恒等元。恒等元在 ρ≠id 时必挂（dist(s,a) = dist(s, ρ(a)) 对所有 s,a 成立强制 ρ = 恒等），而闭包必含恒等元，所以任何非平凡"动作改名"对称在工具层结构性不可能放行。当时实测指纹（收据 cases/mini2048/receipts/ 的 2026-11-03 版，引擎不带 --strict）：g1 拒于恒等元（3/4 元素不过，唯一通过者恰是 rot90 本身）、g3 拒于恒等元（1/2）、g4 拒于恒等元（7/8）；恒等元对照实验双向互证——同一群文件把声明映射换成恒等后 first_bad 变为 rot90，排除"映射选错了"。同模型 g6_pads 照常放行（排除模型坏损），g2（键钉死，740 格）/g5（假群）照常拒答。g3 的声明口径逐格对账 = 0 破坏仍被拒，是那条局限最干净的单点证据。当时的翻案钩子写明："修复归上游 wuxing-gua（逐元素 action_maps，或由生成元映射按同态律推导并验证）；修复后 g1/g3/g4 预期翻案放行——g4 全 D4 压缩读数 4.655×（55 轨道）、g1 3.657×、g3 1.882×——g2/g5 维持拒答、g6 维持放行。"——本节第一段的实跑读数与之逐项相符，钩子兑现。
compare v2 的口径尊重（2026-11-04 更新）：旧版闸门臂无条件 --strict，对 explicit 声明群是错误覆盖。v2 起按群声明分派：声明 explicit → 不加 --strict 原样跑，损害台账按声明口径改名事件后对账（上表带 * 行）；声明 fixed 或无声明 → 维持 --strict。2026-11-04 起声明口径含逐元素映射（对账按每元素各自的 ρ）。声明口径下放行 = 逐格零误差，放行群破坏格 0 依旧是判据性质。
